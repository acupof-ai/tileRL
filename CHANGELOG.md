## 2026-09-05

- **fix** — **`alloc_slot` popped the slot before it zeroed it, so a raise inside `zero_` lost that slot for the life of the process.** `LinearStatePool.alloc_slot` checked `_free`, popped, then zeroed two tensors — and both zeroing steps can raise, by which point the slot has left `_free` and has not reached the caller, so **nothing can ever `free_slot` it**. `Engine.submit`'s unwind cannot compensate: it guards on `slot is not None`, and on this path `slot` is still `None` precisely because `alloc_slot` never returned. Measured with a probe driving the pool directly (`states[slot]` replaced by an object whose `zero_()` raises): **free before=3, after=2 — the pool now offers 2 of 3 slots**, unreachable forever. Slot capacity is the concurrency ceiling (`Engine.__init__` warns when `usable_slots < max_batch`, since a slot is held from submit to finish) and `serve` defaults to `--slots 8` (`cli.py:615`), so eight such failures take concurrency to zero — and the error that follows is `LinearStatePool exhausted` on a pool that should have room, which reads as a config problem rather than a leak. **Reachable on this card:** `errors/2026-09-04-the-recompiles-reproduce-and-are-not-a-shape-set.md:168-172` logs `torch.OutOfMemoryError` with **186.38 MiB free of 31.74 GiB** on this V100; at that margin any allocation raises, `zero_()` included. Fix returns the slot on any post-pop failure. Gated by `test_a_failed_alloc_slot_does_not_consume_the_slot`, which substitutes a raising `zero_`, asserts `len(_free) == 3`, then allocates all three — the last part because a slot can be back in `_free` while the pool is otherwise inconsistent; negative control with the pre-fix body **CAUGHT**. **Found by reviewing a peer's premise, not by a failure:** they asked me to challenge "`alloc_slot` is atomic because it checks `_free` before popping" — checking a precondition before mutating is not being atomic, and the two statements after the pop are the whole defect. `PagedKvPool.alloc_block` was checked for the same shape and does not have it. **Not claimed:** that this leak has occurred in a live run, or that the recorded OOM was inside `alloc_slot` (it was in `silu_mul`).
