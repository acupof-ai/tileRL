# Native fp4 w4a8 load path — cpu (27B numbers pending-remote), 2026-08-26

> Status: Shipped (CPU measured; sm90 perf pending-remote)

## Context

Three defects made the fp4 serving path both wrong and fat, and they were
entangled — none could be fixed alone.

1. The internal fp4 grid was `e2m1fn` = `[0.5, 0.75, 1, 1.5, 2, 3, 4, 6]`,
   which has no zero. The NVFP4 checkpoint is OCP e2m1 = `[0, 0.5, 1, 1.5, 2,
   3, 4, 6]`. Because the grids differed, `load_hf` dequantized the checkpoint
   to bf16 and re-packed it at block 32 — a second lossy quantization on every
   load.
2. A per-channel `[N,1]` FP8 `weight_scale` cannot be expressed in the
   per-128-block `wscale` layout, so those weights were dequantized and
   fp4-packed. On the real 27B that is every FP8 linear in the model.
3. The bf16 master was kept and shipped to the device. `Backend.linear_fp8`
   ended in `return self.linear(x, master)` for every non-CUDA cell, so the
   master was load-bearing at serving, not just training.

The wall-clock metric that matters is 27B decode ms/tick; this host has no
GPU, so the shipped number here is CPU tiny-model throughput (regression
gate) plus the memory arithmetic.

## What Worked

**OCP e2m1 as the one internal grid** (branch-free integer synthesis, one copy
per file). Padded nibbles `0x00` now decode to 0.0 directly, so the zero-padded
`Scale` that used to kill fp4 K-tails is redundant rather than load-bearing.
Round-trip relative Frobenius error on `N(0, 0.02)` weights at block 32:
0.1076 -> 0.1016, max abs error unchanged at 1.23e-2.

**The checkpoint's bytes are the serving format.** `.wq` is byte-identical to
the checkpoint, `.scale` is the checkpoint's block scale widened to f32 with
`B` taken from the tensor shapes (16 for NVFP4, 32 from `pack_fp4`), `.oscale`
is a per-output-row epilogue scale. Block `B` is a call-time kernel parameter,
not a registry entry.

**The e4m3 dequant target must be renormalized.** The w4a8 kernel dequantizes
into e4m3 (`T.cast(w * s, "float8_e4m3fn")`), whose usable range is 448. This
was already broken before the refactor and feeding checkpoint-native
magnitudes in would have made it far worse. Measured on a simulated NVFP4
tensor (N=64, K=256, B=16, w~N(0,0.02)), weight-path relative error against
the f32 dequant:

| `.scale` in | `6*max(scale)` | max rel err |
|---|---:|---:|
| checkpoint e4m3 magnitudes (naive native load) | 2688 | 50.0% |
| `block_max/6` weight units (pre-refactor `pack_fp4`) | 0.083 | 3.8% |
| **renormalized (shipped)** | **10.5** | **2.3%** |

The split is exact: `scale' = scale * 2^-p`, `oscale' = oscale * 2^p` with
`p = floor(log2(max_k scale[n,k]))`. 2.3% is e4m3's own 3-mantissa-bit requant
floor. `tests/test_ops_parity.py::test_fp4_w4a8_e4m3_range` gates it at 3% and
is the only CPU-runnable check on a GPU-only numerics failure.

**Per-channel FP8 stays 8-bit** — `wscale = ones` grid plus the scale in
`.oscale`. One loader branch instead of two, no new kernel.

**No master at serving.** `Backend.materialize` is the load-time conversion
table: fp4 is native on every registered cell; fp8 collapses to one bf16
weight where the cell has no fp8 kernel. `linear_fp8` raises naming the cell
instead of falling back. `keep_master=False` is the default; training passes
`True` and the master is *regenerated* from the served bytes, so the STE
master agrees exactly with what the kernel computes.

**Dispatch is a table.** The 19 `target.startswith("cuda")` / `self.arch ==` /
inline `_resolve(...)` branches in the linear family became `_CUDA_PLAN`, a
`(op, M-regime) -> (kernel, K pad, N cap, N tile)` dict plus a 14-line
`Backend._plan`. Measured over the three method bodies (`linear` +
`linear_fp4` + `linear_fp8`, non-blank lines): **175 -> 88, 49.7%** (spec T5
asked for >=40%), with the pad arithmetic spelled once. Verified behavior-preserving by replaying the pre-refactor
formulas against `_plan` over 5304 (op, M, N, K) shapes: the only differences
are the fp4->e4m3 arms' N pad, and every one of them is a case the old code
got wrong — `Np` was not a multiple of the kernel's hardcoded
`_FP4_BLOCK_N = 64`, so the grid read past the padded `WQ` for
N in {1,4,16,20,32,80,96}. The table pads to a 64 tile and never can.

**27B memory.** fp4 linears are 25.62 G params across 497 tensors.

| | bf16 masters | packed | non-linear (embed etc.) | total |
|---|---:|---:|---:|---:|
| before (master + block-32 repack) | 47.7 GiB | 14.9 GiB | 2.4 GiB | 65.0 GiB |
| **after (checkpoint-native, no master)** | — | **17.9 GiB** | 2.4 GiB | **20.3 GiB** |

`docs/experience/wins/2026-08-26-qwen38-27b-baseline.md` measured 67.9 GiB
resident on the H20, which corroborates the "before" column. The packed side
grows 14.9 -> 17.9 GiB because the checkpoint's B=16 scale grid is twice the
B=32 one — that is the cost of not requantizing, and it buys a 3.2x drop
overall. **pending-remote**: no GPU on this host, so the resident-memory and
decode-ms/tick confirmations are pod work.

## Rule

The e4m3 operand of a w4a8 dequant must be range-normalized, and the removed
factor must be an exact power of two carried in the f32 epilogue. Any fp4
scale that reaches a `cast(w * s, float8_e4m3fn)` needs `6 * max(scale) <= 448`
asserted where it is produced — nothing downstream of that cast can see the
saturation, and no CPU kernel reproduces it.

## Results

CPU tiny model, `TILERL_TARGET=cpu uv run tilerl bench` (prompt_len=128,
gen=32), 6 interleaved before/after runs on the same host, median reported.
"before" is `git archive HEAD` (pre-refactor) on the same interpreter.

| date | commit | machine | target | model | prefill ms/tok | decode ms/tok | throughput tok/s |
|---|---|---|---|---|---:|---:|---:|
| 2026-08-26 | 21facfe (before) | M-series Mac | c (cpu) | tiny | 0.257 | 1.138 | 3885 pf / 878 dec |
| 2026-08-26 | working tree (after) | M-series Mac | c (cpu) | tiny | 0.256 | 1.134 | 3902 pf / 882 dec |

Prefill +0.5%, decode +0.4% — both well inside this host's run-to-run spread
(prefill total ranged 31.4-35.3 ms across 12 runs). The two extra integer ops
per nibble and the `.oscale` epilogue multiply are not measurable at this
scale. `tiny()` is `fp4=False`, so this arm gates the bf16 path against the
dispatch collapse; the fp4 numerics are gated by the parity tests, not by
throughput.

Suite: `TILERL_TARGET=cpu uv run pytest -q` -> **97 passed, 4 skipped**
(baseline 90 before the refactor; +9 new gates, -2 tests of the fp4/fp8
reference backwards, which the refactor deleted along with them).
`TILERL_TARGET=metal uv run pytest -q` -> 97 passed, 4 skipped, 0 failed;
`tests/test_metal_target.py` itself is 4 passed, including the new
cpu-vs-metal fp4 decode parity.

Raw artifacts: none (inline above; the bench prints to stdout).

## Known gaps

- **D1 is narrowed to training checkpoints, not closed.** A master-free
  serving model now round-trips as its own bytes. But a master WINS in
  `save_hf` (it is the weight the optimizer moves), and `cli.py:141` builds
  the training model with `keep_master=True`, so `pretrain(..., ckpt_dir=...)`
  writes zero `.wq` and the reload re-packs at block 32 — measured: a forged
  block-16 key comes back with its scale grid halved, K/16 -> K/32.
- **`Backend.materialize` is called only from `engine.build_engine` and
  `train.train_step`.** A future caller that forwards a model with
  `get_backend()` directly hits `linear_fp8`'s `NotImplementedError`. Named in
  the raise; nothing gates it.
- **Native-e4m3 `.scale` storage** stays a pending-remote A/B (the 2026-08-25
  attempt was a 5-11% decode regression), not part of this work.
- **The two pre-existing metal failures are fixed** (`test_linear_parity`
  with bias, `test_fused_projections_parity`): `Backend.linear` now moves the
  bias to the backend device like it already did the weight, and the four
  `_training_kv` call sites pass `device=backend.device`, which `train.py`
  always documented as required. Metal is 97 passed, 4 skipped, 0 failed.
