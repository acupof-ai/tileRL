# RL training existed only as a comment — 2026-08-29

> Status: Shipped. `tilerl train --rl`, `train.grpo_loop`.

## Context

The standing goal names "RL training" and the tree had none. `train.py` held
three things and not one of them was RL:

- `train_step` — supervised cross-entropy on given tokens.
- `pretrain` — the same over a JSONL corpus.
- `opd_loop` — on-policy DISTILLATION: a frozen EMA teacher generates, the
  student imitates. Behaviour cloning of its own average, no reward anywhere.

No reward, no advantage, no policy gradient. `SamplingParams.logprobs` had been
added with the comment "what a policy gradient needs" and nothing consumed it.
So the gap was capability, not throughput — and I had spent the session before
this measuring the training step's kernel count.

## What Worked

GRPO, because it needs no critic: the group's own mean reward is the baseline,
so one model and one set of weights covers rollout and update.

The whole thing is small, because the policy gradient is not a new training
path. The gradient of `-A * log p(a_t)` w.r.t. the logits is
`A * (softmax - onehot)` — the causal-CE gradient scaled per row by the
advantage. So:

- `_step(...)` was factored out of `train_step`: tape, frozen-base filter,
  finite-step rejection, clip, AdamW. **SFT and RL differ only in `grad_fn`.**
- `rl_step` passes a `grad_fn` that multiplies the CE gradient by the row's
  advantage, masks positions outside `[prompt_len, seq_len)`, and rescales by
  the scored count so the step size does not depend on how much prompt or
  padding is in the batch.
- `group_advantages(rewards, group)` = `(r - mean) / std` per group, and 0 when
  a group ties (no signal, and no division by ~0).
- `grpo_loop` submits the group as ONE engine batch — the group is exactly what
  continuous batching is for — scores it, takes one step.

`_ce_loss_grad` was deleted: after the refactor the callers pass the backend op
directly.

Strictly on-policy, one update per rollout, so the importance ratio is 1 and
there is no clip term. `# ponytail: add the PPO ratio+clip when a rollout is
reused for more than one step.`

## Gates

Two of the four are algebraic, which is what keeps this honest — a "runs
without crashing" test would not notice the RL path silently becoming a second,
subtly different SFT path:

- **A = 1, no prompt, must equal an SFT step parameter-for-parameter** (< 1e-6).
- **A = 0 must be an exact no-op.**
- Right-padding must not reach the gradient (causality makes this exact).
- End to end on the tiny model through the real engine: reward **0.17 -> 1.00**
  in 7 steps and stays there.

```
reward 0.17 0.47 0.69 0.75 0.92 0.86 1.00 1.00 1.00 ...
```

## On the 27B

`tilerl train --model qwen38-27b --rl`, LoRA rank 16, group 4, 16-token
rollouts, H20 GPU 7 — runs, exit 0, reward 0.84 -> 1.00 over six steps.

That number is a smoke test and not evidence of learning: the demo reward
(token id < vocab/2) already scores 0.84 at initialisation, so there is almost
nothing for the update to move. A reward has to start low for its rise to mean
anything, so the same run with a reward over ~6% of the vocabulary:

```
reward 0.406 0.688 0.844 0.984 1.000 1.000 1.000 1.000 1.000 0.688 1.000 1.000
```

**0.406 -> 1.000 in five steps**, held, with one dip at step 10 — group=4 is a
four-sample estimate of the baseline and it is visibly noisy. That is the real
27B, LoRA rank 16, rollouts through the engine.

Getting there needed one fix that is not about RL at all: `cmd_train` built
every model with `keep_master=True`. The bf16 masters exist for full-parameter
quantized training, where the STE gradient lands on them; LoRA trains a FROZEN
base whose backward reads the quantized weight directly and never touches one.
On the 27B that is ~27 GB — it filled the card by itself and OOM'd a
4 x 16-token rollout at 95.21 GiB. The same run afterwards peaks at 59.8 GiB.

## Two ways the rollout was silently off-policy

Both found by reading the engine after the loop worked, not by a failing test:

- **The prefix cache** stores a completed prompt's KV and serves it to the next
  step's rollout — KV computed under the policy of an earlier update.
- **The captured decode graph** bakes the f32 casts of the weights it read at
  capture. The optimizer updates params in place, which invalidates that cache
  on the eager path only; a replay keeps using the old buffer.

Either one makes an on-policy method off-policy and neither ever raises. The RL
engine is built with `prefix_store=NoPrefixStore(), decode_graph=False`, the
requirement is in `grpo_loop`'s docstring, and the end-to-end gate pins the
setting rather than relying on it — the tiny prompt is under `BLOCK_TOKENS`, so
nothing would have published and the test would have passed either way.

## Rule

Check whether the capability exists before optimizing it. Training had a
correctness gate, a throughput row in the baseline, and a CLI flag — and no
reinforcement learning at all. Every one of those signals was about the SFT
path, so none of them was ever going to say the word "reward" was missing.

Corollary, on the test that was wrong first: I asserted that changing prompt
tokens must not move the RL gradient. It must — the prompt conditions every
scored position through the forward pass. Only the *weighting* excludes it. The
code was right and the assertion was wrong; padding is the part that is exactly
excluded, and only because the model is causal.
